# 真机模拟说明（真机数据库 + 全套设备身份）

本文记录**调研结论**与**实测实现**。所有结论都来自本机实测，不是推测。

---

## 一、结论先说

| 问题 | 答案 |
|---|---|
| 有没有「真机数据库」？ | **有**，而且很完整。Google 官方就有 5.4 万台真机清单 |
| 能不能「全套模拟真机」？ | **属性层面可以**（本机已实测成功）；**但过不了 Play Integrity** |
| 指令集要不要模拟？ | **不用**。x86_64 镜像直接跑宿主 CPU，本方案不涉及 ARM 翻译 |

## 二、可用的真机数据库

### 1. Google Play 官方设备清单（已集成，推荐）

- 地址：`https://storage.googleapis.com/play_public/supported_devices.csv`
- 规模：**54,328 台设备 / 3,879 个品牌**，4.59 MB，UTF-16LE CSV
- 字段：`Retail Branding`（品牌）、`Marketing Name`（市场名）、`Device`（代号）、`Model`（型号）
- 性质：Google 自己维护，**是 Play 商店判断设备兼容性的权威来源**，100% 真实
- 本机已下载到 `_data/supported_devices.csv`

### 2. pif.json / pif.prop 指纹库（了解即可，**不建议用**）

- 代表仓库：`osm0sis/PlayIntegrityFork`（最权威、活跃维护）、`daboynb/autojson`
- 格式：一份 JSON/prop，含 `MANUFACTURER/MODEL/FINGERPRINT/PRODUCT/DEVICE/SECURITY_PATCH` 等
- **致命问题**（来自 PlayIntegrityFork 官方 README 原文）：
  - 公开共享的指纹**会被 Google 封禁**，只有 "private fingerprints"（私有不公开的）才可能有效
  - Pixel Beta/Canary 指纹**已经无法通过 DEVICE integrity**，只能配合 Tricky Store 走 STRONG
  - 要过 STRONG integrity 还需要**未吊销的硬件 keybox**（真实 TEE 硬件密钥）
- 而且它的工作方式是在**真机上**用 Magisk/Zygisk 注入 Play Services 进程，**不适用于模拟器**

> 一句话：公开指纹库里的东西基本都已被封，靠它过检测这条路已经走不通。

## 三、本机实测实现（真的改成功了）

### 3.1 关键发现：怎么改掉 `ro.product.*`

`ro.*` 属性是**写一次即锁定**的，实测三条路都失败：

| 方法 | 结果 |
|---|---|
| `setprop ro.product.model X`（已 root） | ❌ `Failed to set property` |
| `emulator -prop ro.product.device=komodo` | ❌ 值不变 |
| `-prop ro.adb.secure=0` | ❌ 值不变 |

**唯一可行路径**（已实测通过）：

```
1. 用 -writable-system 启动模拟器
2. adb root                                  # 需要 userdebug 镜像
3. adb remount                               # 会 disable-verity 并对各分区启用 overlayfs
   → 输出 "Verity disabled; overlayfs enabled. Now reboot your device"
4. adb reboot                                # 让 overlayfs 生效
5. adb root && adb remount                   # 再次 remount，此时 /system 等为可写
6. 改写 build.prop（就地替换对应行）
7. adb reboot
```

改写后 overlayfs 的上层文件存放在 `/mnt/scratch/overlay/<分区>/upper/`，
数据落在 `/data`，**随 userdata 持久化**——实测模拟器完全重启后身份依然保留。

### 3.2 要改哪些文件

生效值来自**分区级**属性，不是 `/system/build.prop`：

| 文件 | 内容 |
|---|---|
| `/product/etc/build.prop` | `ro.product.product.{brand,device,manufacturer,model,name}` |
| `/system_ext/etc/build.prop` | `ro.product.system_ext.*` |
| `/vendor/build.prop` | `ro.product.vendor.*` |
| `/system/build.prop` | `ro.build.{id,version.*,type,tags}`、`ro.product.first_api_level` |

`ro.build.fingerprint` **不需要手写**——它由 init 在启动时用
`ro.product.brand/name/device` + `ro.build.version.release/id/incremental/type/tags` 自动拼出来，
所以改了 `ro.product.*` 后指纹会跟着变（已实测）。

## 四、能力边界（重要）

### 4.1 能改的

- `ro.product.{brand,device,model,name,manufacturer}` —— 全套真实设备身份
- `ro.build.{id,version.release,version.incremental,type,tags,version.security_patch}`
- `ro.product.first_api_level`
- `ro.build.fingerprint`（由上面这些自动推导，跟着变）

### 4.2 改不了的（硬限制）

| 项 | 为什么 |
|---|---|
| **GLES 扩展 `ANDROID_EMU_*`**（30+ 个） | gfxstream 硬编码，任何 props 都改不掉 |
| **GPU 渲染器 `Android Emulator OpenGL ES Translator`** | 同上，这是模拟器图形栈自报的名字 |
| **CPU 型号 `GenuineIntel / i9-13900H`** | 来自真实 CPUID，改 props 会与硬件事实冲突 |
| **Play Integrity 硬件证明** | 需要真实 TEE 硬件密钥，数据库给不了 |

### 4.3 Play 镜像的额外限制

- Play 商店镜像是 **user 版本**（`ro.debuggable=0`），`adb root` 会失败
- 因此**属性改写只在 ATD 镜像上可行**（`ro.debuggable=1`）
- 取舍：
  - **ATD 镜像** = 能改全套身份，但没有桌面/设置 UI
  - **Play 镜像** = 有完整 UI + Play 商店，但改不了身份

> 如果既要 UI 又要改身份：可在 ATD 上用 `adb install` 侧载一个启动器 APK 获得桌面。

### 4.4 关于过应用风控

**本方案过不了 Play Integrity。** 原因不是配置问题，而是上面 4.2 里的三项硬限制 +
公开指纹已被封禁。属性伪装只能骗过那些**只读 `Build.MODEL` / `Build.FINGERPRINT`**
的简单判断，遇到做 GLES 探测或硬件证明的风控会立刻暴露。

需要真正过风控，只有：**实体真机 / 云真机 / redroid（需 root 真机）**。

## 五、怎么用

### 命令行（在 `app` 目录）

```bash
# 数据库
node tools/profile-cli.js db
node tools/profile-cli.js search "Galaxy S23"

# 从数据库生成一份档案
node tools/profile-cli.js make "Pixel 9 Pro XL"

# 查看 / 应用 / 还原
node tools/profile-cli.js show
node tools/profile-cli.js apply samsung_s23_ultra
node tools/profile-cli.js revert
```

### 图形界面

「硬件设置」页 → **真机档案（全套设备身份）** 卡片：
搜索真机 → 填档案名或型号 → 「应用并重启」→「当前身份」验证。

### 前提条件

1. 镜像必须是 **ATD**（`state.json` 里 `"engine": "atd"`）
2. 启动时带 `-writable-system`（`state.json` 里 `"writableSystem": true`，默认已开）
3. 首次应用时若提示 "system 仍为只读，需要先重启一次"，重启虚拟机后再点一次即可

### 还原

- 「还原」按钮 / `revert` 命令：删除 overlayfs 上层副本 + 重启，回到镜像原始身份
- 彻底恢复出厂：删除 `avd/A14_Root.avd/userdata-qemu.img.qcow2`

## 六、在「有谷歌环境」的前提下做属性改写（已打通）

### 6.1 关键突破：`google_apis` 镜像

之前有个死结：Play 商店镜像有完整 GMS 但 `ro.debuggable=0` 不能 root；ATD 能 root 但没有桌面。
实测发现第三条路 —— **`google_apis` 镜像（不是 playstore）同时满足两者**：

| 镜像 | GMS | 桌面 UI | `ro.debuggable` | 能否改属性 |
|---|---|---|---|---|
| `google_apis_playstore`（Play 商店） | ✓ | ✓ | **0** | ❌ 不能 root |
| `google_atd`（ATD） | ✓ | ❌ 无桌面 | 1 | ✓ |
| **`google_apis`** | ✓ | **✓** | **1** | **✓ 可 root** |

实测结果（本机验证）：

```

```

桌面截图可见 Gmail / Photos / YouTube / Chrome / 电话 / 短信全部正常，Google 搜索栏可用。

切换命令：

```bash

```

### 6.2 ARM 软件层伪装（实测结论）

**好消息**：`google_apis` 镜像自带 `libndk_translation.so`（NDK 二进制翻译层），
`ro.dalvik.vm.native.bridge=libndk_translation.so`、`ro.enable.native.bridge.exec=1`，
所以 **ARM64 代码是真的能在这台 x86 模拟器上执行的**，不是纯改字符串。

**能做到的**：把 `arm64-v8a` 提到 ABI 列表首位，让 `Build.SUPPORTED_ABIS[0]` 报告 `arm64-v8a`。

**关键坑位（都是实测踩出来的）**：

| 做法 | 结果 |
|---|---|
| 改 `ro.product.cpu.abilist`（system/vendor） | ❌ 不生效，ODM 优先级最高 |
| 改 `/odm/etc/build.prop` 的 `ro.odm.product.cpu.abilist` | ✅ **生效** |
| 同时把 `ro.product.cpu.abi` 改成 `arm64-v8a` | ❌ **系统崩溃**：引导耗时 250 秒、`package` 服务消失、GMS 变僵尸进程 |
| 只改 abilist 顺序、`abi` 保持 `x86_64` | ✅ 系统健康（288 服务） |

原因：`ro.product.cpu.abi` 决定系统库/zygote 的加载路径，系统库只有 x86_64 版本，
改成 arm64 就找不到可加载的库。所以 **`abi` 必须保持 `x86_64`**。

当前工具已内置保护：若档案里 `cpu.abi` 含 `arm`，会直接拒绝并说明原因。

### 6.3 硬件标识改写

| 属性 | 原值 | 改为 | 结果 |
|---|---|---|---|
| `ro.product.board` | `goldfish_x86_64` | `kalama`（骁龙 8 Gen 2 主板名） | ✅ 可改 |
| `ro.board.platform` | （空） | `kalama` | ✅ 可改 |
| `ro.hardware` | `ranchu` | — | ❌ **不能改** |

`ro.hardware=ranchu` 不能动的原因：`/vendor/lib64/hw/` 下 `graphics.mapper`、`sensors`、
`audio` 只有 `.ranchu.so` 变体（没有通用版），改了会导致 HAL 加载失败 → 黑屏/无声。

### 6.4 改完之后还剩哪些暴露点（诚实清单）

| 检测项 | 实际值 | 能否消除 |
|---|---|---|
| `ro.hardware` | `ranchu` | ❌ 改了就黑屏 |
| `ro.boot.qemu` / `ro.boot.qemu.*` | `1` / 一堆 | ❌ 来自内核 cmdline，build.prop 覆盖不了 |
| `init.svc.qemu-*` / `init.svc.goldfish-*` | 多个 running | ❌ init 服务名 |
| `/proc/cpuinfo` | `13th Gen Intel i9-13900H` | ❌ 内核生成 |
| `Build.CPU_ABI` | `x86_64` | ❌ 改了系统崩 |
| GLES 渲染器 | `Android Emulator OpenGL ES Translator` | ❌ gfxstream 硬编码 |
| GLES 扩展 | 30+ 个 `ANDROID_EMU_*` | ❌ 无法消除 |
| Play Integrity 硬件证明 | 无真实 TEE | ❌ 数据库给不了 |

**结论**：能做到「**Google 环境可用 + 全套身份属性 + SUPPORTED_ABIS 报 arm64 + ARM 代码可执行**」，
这已经骗得过只读 `Build.MODEL/FINGERPRINT/SUPPORTED_ABIS/board` 的检测；
但做 `/proc/cpuinfo`、GLES 探测、`init.svc` 扫描或硬件证明的检测，仍然会识别出模拟器。

### 6.6 持久化机制（重要）

**overlayfs 的改动不跨「模拟器进程重启」**。实测结论：

| 操作 | 伪装是否保留 |
|---|---|
| `adb reboot`（guest 重启，模拟器进程不变） | ✅ 保留 |
| 完全停止模拟器再启动 | ❌ 丢失，回到镜像原始值 |

原因：`adb remount` 用 overlayfs 保存改动，上层目录在临时 scratch 里，
模拟器进程退出后 scratch 被丢弃。

因此实现了**启动后自动补应用**：每次冷启动后检查当前身份是否匹配
`_data/active-profile.json` 里的档案，不匹配就自动重写并重启（内部最多 3 轮）。

- 代价：冷启动耗时从 ~25 秒增加到 **~200 秒**（含补应用时的重启）
- 若想避免这个开销：**应用档案后只用 `adb reboot` 重启**，不要完全停止模拟器

## 七、已修复的相关缺陷

调研过程中发现并修复了三个真实 bug：

1. **切换镜像后引导卡死**：`setEngine` 没有清空 userdata，而不同镜像的 userdata 不兼容
   （实测 Play 的 userdata 配 ATD 镜像会卡在引导）。已改为切换时自动 `resetUserdata()`。
2. **清理逻辑会误删用户数据**：`cleanStale()` 原本每次启动都删 `userdata-qemu.img`，
   等于每次开机清空数据。已移除该删除项。
3. **`setEngine` 不同步 config.ini**：只改 `state.json` 不改 AVD 的 `config.ini`，
   直接用命令行启动时会仍用旧镜像。已补上 `applyConfigToAvd()`。

另外增加了 `.engine` 标记文件：记录当前 userdata 属于哪个镜像，
启动时发现不一致会自动清空，避免残留状态导致引导卡死。

## 八、故障排查

### 启动后卡在「启动中」/ adb 一直 offline

典型原因是**残留的镜像相关文件与当前镜像不匹配**。按顺序清理后重启：

```powershell
# 1. 杀掉所有模拟器进程
Get-Process | Where-Object { $_.ProcessName -match 'qemu|emulator' } | Stop-Process -Force
# 2. 停 adb server
.\android-sdk\platform-tools\adb.exe kill-server
# 3. 删除 AVD 运行态文件（userdata 会重新生成，数据丢失）
Get-ChildItem avd\A14_Root.avd -File |
  Where-Object { $_.Name -match 'qcow2|hardware-qemu|\.lock|emu-launch|bootcompleted|initrd|read-snapshot|userdata-qemu' } |
  Remove-Item -Force
```

### 应用档案时报「system 仍为只读」

第一次 `remount` 只做 disable-verity + 启用 overlayfs，**需要重启一次**才真正可写。
本工具已自动处理（remount → 重启 → 再 remount → 写入 → 重启），无需手动干预。
若仍失败，确认启动参数里确实有 `-writable-system`。

### `adb root` 失败

说明当前是 **user 版本镜像**（Play 商店镜像，`ro.debuggable=0`）。
属性改写只能在 **ATD 镜像**（`ro.debuggable=1`）上做：

```bash
node -e "new (require('./src/vm').VmManager)().setEngine('atd')"
```
